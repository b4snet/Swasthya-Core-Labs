# ADR-0005: API-First with Contract and Versioning Discipline

- **Status:** Accepted
- **Date:** 2026-09-16
- **Owner:** Architecture

## Context

All product behavior must be consumable via APIs (internal and external).
Undisciplined contract evolution would break integrations.

## Decision

- **API-first**: every capability is delivered through versioned HTTP APIs;
  OpenAPI documents are the contract.
- **Versioning policy**: explicit API versioning strategy (URI or header —
  decided in API phase); additive changes in-version; breaking changes in a
  new version; deprecation windows documented.
- FHIR endpoints publish a **CapabilityStatement** where FHIR is used.
- Internal services reuse the same contract discipline; no hidden bypasses.
- Error model: structured, standardized (FHIR `OperationOutcome`-aligned
  where appropriate).

## Consequences

- **Positive:** stable integration surface; contract testing feasible;
  OpenAPI-native tooling.
- **Negative:** versioning adds process overhead; early APIs must be designed
  carefully to minimize churn.
