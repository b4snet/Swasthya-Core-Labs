# ADR-0008: Configuration-Driven Clinical and Jurisdictional Rules

- **Status:** Accepted
- **Date:** 2026-09-16
- **Owner:** Architecture

## Context

Reference intervals, flags, rejection reasons, QC rules, retention schedules,
and interop profiles vary by facility and jurisdiction. Hard-coding them
would be incorrect and require shipping "clinical rules" — explicitly
disallowed until authorized.

## Decision

- Clinical/jurisdictional variability is **configuration (data) with
  provenance and version history** — never program logic.
- The configuration subsystem is a first-class module with audited change
  control and environment/facility scoping.
- Content (reference ranges, thresholds, flags, QC rule sets) is **not
  invented by the platform**; it is provided by authorized clinical/
  laboratory sources under governance.
- This decouples rules from releases: schema/API changes remain code;
  rules/values travel as versioned configuration.

## Consequences

- **Positive:** jurisdiction-configurability; validation scope moves to
  configuration governance; no fabricated clinical content in code.
- **Negative:** requires configuration authoring/governance tooling and
  migration discipline in later phases.
- See `docs/quality/quality-architecture.md`, `docs/architecture/
  domain-boundaries.md`.
