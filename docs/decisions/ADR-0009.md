# ADR-0009: Phase 1 Identity and Auth Context Model

- **Status:** Accepted
- **Date:** 2026-09-16
- **Owner:** Architecture / Security

## Context

Phase 0 (ADR-0007) deferred the concrete identity/tenancy design. Phase 1
needs a working server-side auth context: resolve an authenticated caller to
an internal principal and its organization/facility-scoped grants before any
data access. The platform must stay identity-provider-neutral while never
treating a raw `client_id` as proof of identity.

## Decision

- **Tokens are validated first, mapped second.** JwtBearer validates
  signature, issuer, audience, and lifetime against a configured contract
  (`Authentication:Issuer/Audience` + `SigningKeyBase64` or `JwksUrl`).
  Inbound claim mapping is disabled (`MapInboundClaims = false`) so the
  literal `sub`/`iss` claim types are read directly.
- **`client_id` is never treated as identity.** The identity is formed from
  the *validated* `iss` + `sub` claims. Principal type is derived only from
  the configured type claim (`Authentication:PrincipalTypeClaim`,
  default `principal_type`), where the configured service value
  (`Authentication:ServicePrincipalTypeValue`, default `service`) marks a
  service principal; anything else is a human principal.
- **Server-side resolution:** the API resolves the JWT identity to an
  internal `Principal` (issuer + external subject + type) and loads grants.
  Unknown or inactive principals are denied (403). An `AuthContext` is
  stored in `HttpContext.Items` for the request.
- Password/refresh-token identity and enrollment/administration are **out of
  scope** for Phase 1 (identity providers are INTEGRATION).

## Consequences

- **Positive:** provider-neutral JWT contract; no spoofable `client_id`
  trust; service principals are first-class and testable.
- **Negative:** requires pre-provisioned principals for any authenticated
  access; roles/assignments are managed out of band in Phase 1.
- See `docs/security/security-architecture.md`, ADR-0010, ADR-0013.
