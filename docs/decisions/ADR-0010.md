# ADR-0010: Facility-Scoped RBAC with Application-Level Enforcement

- **Status:** Accepted
- **Date:** 2026-09-16
- **Owner:** Architecture / Security

## Context

Reads and future writes must be scoped to organizations and facilities.
Phase 1 enforces isolation and decides where that enforcement lives.

## Decision

- **Deny-by-default RBAC.** Access is granted only through
  `principal_role_assignments → role → role_permissions → permission`,
  scoped to an organization and optionally a facility. Guards
  (`PermissionGuard`) and query services filter results by the caller's
  grants; organization-wide and facility-scoped grants are distinct.
- **No Row-Level Security (RLS) in Phase 1.** Enforcement is in the
  Application layer via `AuthContext` grants. Contracts (filtered
  repositories, `PermissionGuard`) keep this swappable for a future
  `SET LOCAL` tenant-context model without changing the public surface.
- **Audit writes are scoped like reads:** a caller cannot write audit rows
  for organizations they cannot read; organizational scope is never empty
  (`Guid.Empty` is rejected).
- Deactivation of an organization, facility, or role removes its grants at
  resolution time (queries filter on `EntityStatus.Active`).

## Consequences

- **Positive:** clear, testable isolation; no Phase 1 DB-PERMISSION/RLS
  complexity; cross-tenant access is denied and auditable.
- **Negative:** every data access path must consult grants (enforced by
  review + tests); RLS/`SET LOCAL` is future work (documented, not
  implemented).
- See ADR-0009, ADR-0011, ADR-0014, `docs/security/security-architecture.md`.
