# ADR-0011: Persistence Foundation with EF Core 10, PostgreSQL, and xmin

- **Status:** Accepted
- **Date:** 2026-09-16
- **Owner:** Architecture

## Context

Phase 1 needs a durable, evolvable persistence foundation for identity,
tenancy, RBAC, and audit. Concurrency control must be field-proven against
the exact dependency versions used.

## Decision

- **EF Core 10 (LTS) + Npgsql on PostgreSQL 17.** Migrations are generated
  with the pinned local tool (`dotnet-ef`), Snake-case naming via
  `EFCore.NamingConventions`.
- **Optimistic concurrency by `xmin`.** All mutable entities have
  `uint Version` mapped with `IsRowVersion()`. Verified against
  Npgsql.EntityFrameworkCore.PostgreSQL **10.0.3**: the generated migration
  maps it to the PostgreSQL system column `xmin`
  (`type: "xid", rowVersion: true`); no custom mapping or triggers needed.
- **Design-time isolation:** the `DesignTimeDbContextFactory` reads the
  `SCL_DB_CONNECTION` environment variable; the host registers persistence
  only when `ConnectionStrings:CoreLabs` is present, so the API can serve
  health/version/openapi without a database while `/v1` endpoints require
  persistence.
- **Referential integrity:** FK-restrict on mutable identity references; no
  soft-delete in Phase 1; status fields deactivate.

## Consequences

- **Positive:** proven concurrency semantics; migration discipline;
  snake_case DB consistent with naming conventions.
- **Negative:** a state-changing client must handle `DbUpdateConcurrencyException`;
  migrations are generated by tool into `Infrastructure/Persistence/Migrations`.
- See ADR-0001, ADR-0010, ADR-0012, ADR-0014.
