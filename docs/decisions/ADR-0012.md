# ADR-0012: Append-Only Audit with Allowlisted Metadata

- **Status:** Accepted
- **Date:** 2026-09-16
- **Owner:** Architecture / Security

## Context

Audit records must be trustworthy and tamper-evident-by-construction without
inventing PHI-redaction machinery. Phase 0 principles (ADR-0006) require
immutable, provenance-tracked records.

## Decision

- **Append-only enforced at the database level.** The `IdentityTenancyFoundation`
  migration creates a PL/pgSQL trigger (`prevent_audit_record_mutation`,
  `trg_audit_records_append_only`) that raises `55000` for any `UPDATE` or
  `DELETE` on `audit_records`. Inserts are unrestricted.
- **Explicit metadata allowlist.** `AuditMetadata` admits exactly
  `request_method`, `request_path`, `http_status`, `reason`, `failure` —
  non-PHI, ≤200 characters, unknown keys throw. There is **no generic PHI
  regex redaction**; sensitive content is simply not admitted as audit
  metadata.
- **Correlation and provenance:** every record carries `correlation_id`
  (validated per request header), actor (principal id/type), organization
  and optional facility scope, resource type/id, action, outcome, and UTC
  timestamps. Metadata is stored JSONB.
- Writes flow through `AuditRecordFactory` + `IAuditRepository`; the API's
  `/v1` endpoint group commits audit rows in the same request (endpoint
  filter → `IUnitOfWork.SaveChangesAsync`).

## Consequences

- **Positive:** provable append-only behavior (tested against live PG);
  predictable, safe metadata; no PHI-in-metrics surface.
- **Negative:** corrections to audit data are impossible by design (other
  records annotate); storage is write-once.
- See ADR-0006, ADR-0013, ADR-0014, `docs/clinical/clinical-data-integrity.md`.
