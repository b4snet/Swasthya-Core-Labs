# ADR-0013: API Security Conventions

- **Status:** Accepted
- **Date:** 2026-09-16
- **Owner:** Security

## Context

The API surface needs uniform, safe behavior for correlation, errors,
authentication, authorization, and abuse control.

## Decision

- **Correlation IDs:** `X-Correlation-Id` is read (ASCII letters/digits,
  `-_.`, ≤100 chars), otherwise generated. The value is echoed on every
  response and flows into audit records.
- **Error model:** Problem Details JSON. `NotFoundException` → 404,
  `PermissionDeniedException` → 403, everything else → a generic 500 with
  guidance; internal exception details are never returned to clients.
- **Authentication:** JwtBearer per ADR-0009. **Authorization:** a single
  `identity-tenancy` policy resolves the `AuthContext` once per request and
  stores it on `HttpContext`.
- **Rate limiting:** global fixed-window limiter (100/min per remote IP)
  with `429 Too Many Requests` (`RateLimitingMiddleware`).
- **Middleware order:** Correlation → ErrorHandling → RateLimiter →
  Authentication → Authorization.
- **Production fail-fast:** startup requires Issuer, Audience, connection
  string, and a signing key or JWKS URL.
- **API versioning:** `/v1` URL-prefix on the identity/tenancy surface.

## Consequences

- **Positive:** defensible, testable web conventions; consistent client
  experience; abuse and correlation support from day one.
- **Negative:** customers cannot customize error texts; rate limits are
  global (per-route tuning is future work).
- See ADR-0009, ADR-0010, ADR-0012, `docs/security/security-architecture.md`.
