# ADR-0019: Master Roadmap and System Blueprint Adoption

- **Status:** Accepted
- **Date:** 2026-09-17
- **Owner:** Architecture

## Context

Phase 2 (laboratory organization and master-data foundation) is accepted and
frozen. The project adopted two authoritative master documents:

1. **Master Architectural Roadmap** — the long-term north star defining product
   vision, domain model, implementation sequence, review cycles, and
   governance ([`ROADMAP.md`](../../ROADMAP.md)).
2. **Master System Blueprint** — the target architecture and system map
   (what we are building, how the pieces relate, what belongs in each layer)
   ([`master-blueprint.md`](../architecture/master-blueprint.md)).

The repository previously used a **coarse phase numbering** in `ROADMAP.md`
(Phases 0–6, e.g., a single "Phase 3 — Clinical Domain" lumping service
catalog, specimens, accessioning, worklists, results, validation, and
reporting). This conflicted with the master roadmap's granular numbering
(Phases 0–55, e.g., Core Laboratory = Phases 3–10, Device Integration =
Phases 23–26, Enterprise Interoperability = Phases 40–44, Quality = Phases
45–46). In addition, the master documents' CURRENT POSITION sections were
outdated (Phase 2 was complete but not marked accepted/frozen).

Per the roadmap's governance rule, conflicts between the roadmap, the
repository, security invariants, clinical requirements, and external standards
must be investigated and documented rather than resolved silently.

## Decision

- **Adopt** the Master Architectural Roadmap as the authoritative
  implementation direction and the Master System Blueprint as the authoritative
  target-architecture reference for the project.
- **Replace** the repository's coarse `ROADMAP.md` phase scheme with the
  master 0–55 numbering. Future references to phases in code, tests, docs,
  ADRs, and changelogs use the master numbers.
- Update the roadmap's and blueprint's CURRENT POSITION to reflect the actual
  state: Phase 0 → ACCEPTED, Phase 1 → ACCEPTED / GREEN / FROZEN,
  Phase 2 → ACCEPTED / GREEN / FROZEN, Phases 3+ → PLANNED.
- **Phase advancement is not automatic.** Each future phase (starting with
  Phase 3 — Laboratory service catalog and diagnostic request/order
  foundation) requires its own execution specification and explicit
  authorization before implementation, per the roadmap's phase execution and
  governance sections.
- Phase boundaries may be refined only through documented architectural
  review; such changes are recorded rather than made silently.
- The blueprint's validation language (PROVEN LOCALLY / SIMULATED /
  CONTRACT-TESTED / DOCUMENTED / ARCHITECTURALLY DEFINED / REQUIRES FUTURE
  IMPLEMENTATION) is the standard terminology for capability claims in this
  repository.

## Consequences

- **Positive:** unambiguous phase references; a canonical home for the
  roadmap and blueprint as source-of-truth documents consistent with
  `AGENTS.md`; architecture review points are explicit (after Phases 5, 10,
  15, 22, 31, 39, 44, 49).
- **Negative / watch:** existing docs that referenced coarse phases
  (e.g., "Phase 3/4/5/6") were remapped to the master numbering; any
  remaining coarse-phase reference is stale and must be corrected during doc
  reviews.
- See ADR-0003 (modular architecture) and ADR-0015 (laboratory organization
  model) for the architecture the blueprint extends.
