# ADR-0021: Laboratory Result Entry & Observation Completion (Phase 7)

Status: **Accepted**

Date: Phase 7 freeze

## Context

Phases 1–6 established identity/tenancy/RBAC, append-only audit, core persistence,
laboratory master data, specimen foundation, diagnostic order/request lifecycle,
and result-data-type/unit/reference-interval foundations. Phase 7 implements the
**Laboratory Result Entry & Observation Completion** slice: capturing result
observations for an order item, typing their values, and providing create/list/
retrieve/update entry-points — without clinical validation, verification,
finalization, or controlled-correction behavior (those are Phase 8).

Per ADR-0019 (0–55 roadmap), Phase 7 is the final entry/observation phase. It must
not leak Phase 8 behavior: no verification/validador/finalization workflows, no
result amendment/correction pathways, no Phase 8 statuses.

## Decision

- Phase 7 = **Laboratory Result Entry & Observation Completion** (this ADR).
- Phase 8 = **Result Validation, Verification, Finalization & Controlled Correction**
  (explicitly **out of scope**; documented as the forward boundary in ROADMAP,
  CHANGELOG, README, and this ADR).
- Implement a `results` table introduced by a dedicated Phase 7 migration
  `20260918035033_AddResultEntity` (create/list/get-by-id/update surface;
  append-only audit preserved from earlier phases).
- Result observations are typed (numeric / textual / coded / unit UCUM), stored
  as separate typed columns with a single value-type discriminator, consistent
  with ADR-0018 reference-interval / data-type foundations.
- Entry captures ordering integrity: a result belongs to an order item and a
  specimen, and to the test version current for that item at entry.
- Facility/organization isolation is enforced on every result endpoint via the
  established tenancy/RBAC policy; authorization is not bypassed to make startup
  or tests succeed.
- Concurrency: Phase 7 result **entry** adopts the append-only/immutable guidance
  of ADR-0006 for created observations; editable result **update** behavior is
  deliberately narrow (Phase 7 scope) and does not introduce Phase 8
  verify/finalize/amend transitions.

## Consequences

- **Positive:** Phase 7 closes the clinical-results entry foundation while keeping
  the Phase 7 → Phase 8 boundary authoritative: Phase 8 adds validation,
  verification, finalization, and controlled correction on top of Phase 7 without
  re-architecture.
- **Positive:** Disposable-PostgreSQL-backed tests genuinely execute the Result
  repository against a real database (not skipped).
- **Negative / boundary:** Phase 7 does NOT implement clinical validation,
  regulatory compliance, certification, live analyzer integration, live HMS/EHR
  integration, verification/finalization, or controlled correction. Those are
  Phase 8 (and external/environment) items and are documented, not implemented.
- **Git baseline limitation:** the repository has no committed baseline (all files
  untracked); commit-to-commit diff review is not applicable Fact-to-Phase 7.
  Working-tree review was performed in lieu.

## Phase 8 boundary (authoritative)

- Phase 7 = Laboratory Result Entry & Observation Completion → **this freeze**.
- Phase 8 = Result Validation, Verification, Finalization & Controlled Correction
  → **not started**; no Phase 8 implementation, migration, or status has been added.
