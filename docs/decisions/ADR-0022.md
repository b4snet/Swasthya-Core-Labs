## Context

Phase 7 implemented laboratory **result entry and observation completion**
(`results` table, migration `20260918035033_AddResultEntity`) with typed
numeric / textual / coded / unit-bearing values, specimen and order-item
association, and editable update constrained to the `"entered"` state. Phase 7
explicitly **deferred** result validation, verification, finalization and
controlled correction (deferral boundary: `ROADMAP.md` Phase 8,
`docs/architecture/master-blueprint.md` section 34 "**Phase 8 ... has NOT been
started** ... must not begin without explicit authorization").

Phase 8 (result validation → verification → finalization → controlled
correction) is now authorized.

Four ordering questions must be resolved before Phase 8 implementation begins.
This ADR records the decisions. Where a decision is not established by the
existing repository or authoritative documentation, it is recorded as
**UNRESOLVED — REQUIRES EXPLICIT DECISION** and no earlier-phase migration,
API, permission, or persistence invariant is modified.

## Non-negotiable invariants (inherited from Phase 7, not re-litigated)

- `Result.StatusCode` remains `string`.
- `Result.Version` remains `long`.
- Finalized clinical data must never be silently overwritten or deleted.
- Original finalized results are preserved; history is reconstructable.
- No silent overwrite of any observation value.
- Organization / facility isolation remains server-derived; no forged
  claims expand scope.

## Decision 1 — Validation / Verification Editability

### Definition of "validation"

Three distinct meanings exist and are deliberately separated:

1. **Structural validation (Phase 7, implemented):** value typedness — a
   numeric value with a unit, textual, or coded value, per
   `Result.ValueTypeCode` and the Phase 6 value-type rules. Already enforced
   at entry/persistence (`ResultRepository.CreateAsync`).
2. **Clinical/process validation (Phase 8):** the authorized, governed
   step that evaluates whether an entered result may proceed toward
   verification. It is a **process gate**, not a re-statement of structural
   rules.
3. **Verification (Phase 8):** an authorized actor attests the result is
   correct and appropriate for release, before finalization, and records
   actor + timestamp.
4. **Finalization (Phase 8):** the authorized act that makes the result
   clinically final and immutable without a controlled correction.

Phase 8 also introduces a distinct **validated** process state from
**entered**; structural validation predicates the Editable→ValidatedEligible
transition eligibility, but clinical/process validation is a separate
governed gate (see Decision 2).

### RESOLVED — structural validation

Structural validation is already implemented (Phase 7) and is **not
re-implemented or changed** in Phase 8. Phase 8 consumes its result.

### UNRESOLVED — clinical/process validation semantics

Whether "validation" in Phase 8 expresses:
- (a) a **required, governed process gate** (with state),
- (b) a **transient evaluation** (recomputed on demand), or
- (c) both,

is **not established** by the current repository or documentation.
**UNRESOLVED — REQUIRES EXPLICIT DECISION** — do not invent, encode, or
ship an interpretation of the clinical gate. Phase 8 implementation cannot
proceed until (c) or ((a) or (b)) is chosen.

### Editability

RESOLVED: `entered` is the only caller-writable ordinary state; it is
preserved. Any transition to realized Phase 8 states must be explicit and
authorized (never an implicit side effect).

UNRESOLVED: whether a result in a Phase 8 `validated` state remains
editable before verification — **REQUIRES EXPLICIT DECISION**.

UNRESOLVED: whether a `verified` result remains editable before
finalization — **REQUIRES EXPLICIT DECISION**. (Phase 7's
`Result.UpdateValue` already gates writes to `StatusCode == "entered"`;
whether verification is an additional lock is not established.)

RESOLVED: a **finalized** result is **not editable** by ordinary update;
any change requires the controlled-correction path (Decision 3).

## Decision 2 — Concurrency

### Existing mechanism (ground truth)

The repository already implements PostgreSQL-native optimistic concurrency on
every aggregate via the EF `IsConcurrencyToken()` on a `Version` property
mapped to the PostgreSQL `xmin` system column (verified in Phase 6–7
migrations/designer/snapshot: `IsConcurrencyToken().HasColumnName("xmin")`).
The Phase 7 `results` entity follows the same convention.

### RESOLVED — concurrency mechanism

Phase 8 **reuses the existing `xmin`-based optimistic concurrency token on
`Result.Version` (long)**. It does not invent a new concurrency mechanism.

- Simultaneous verification, finalization, or correction is detected by the
  EF concurrency token; the first writer wins, subsequent writers receive a
  concurrency conflict.
- Stale client versions (an entity read earlier with an obsolete `Version`)
  fail on write; the client must re-read and re-apply.
- Duplicate lifecycle transitions are prevented because the guarded state
  transition (e.g. `entered→validated`) can only be performed from the
  current state; once `Validated`, a second transition attempt fails.
- No `Result.Version` redesign; no new concurrency column.

### Conflict semantics

RESOLVED: on a write conflict the action fails atomically with 409-style
concurrency semantics, using the existing safe error mapping; no partially
committed transition is observable. (Enforcement/boundary specifics are an
implementation detail to be verified against real PostgreSQL in Phase 8.)

## Decision 3 — Controlled Correction Payload

### Non-negotiable constraints (inherited, not optional)

- The finalized result is **never overwritten**.
- The original finalized result is **preserved**.
- History must permit reconstruction of
  `original finalized → correction → current effective`.
- Correcting actor, timestamp, and where mandated, reason are recorded.
- No generic audit-based history substitute: clinical-history representation
  is distinct from administrative audit.

### UNRESOLVED — correction representation

Whether a correction:
- (a) creates a **new Result identity** (a successor row that becomes the
  effective result, linked to its predecessor), or
- (b) is represented as a **versioned amendment on the same result identity**
  (a new amending observation tied to the original), or
- (c) both,

is **not established** by the current repository or documentation.
**UNRESOLVED — REQUIRES EXPLICIT DECISION.**

### UNRESOLVED — correction payload fields

Which fields a correction may alter (value, unit, datatype, observed time,
entered-by, specimen/order-item/test-version linkage, or subset), and whether
a prior reason/justification is mandatory:
**REQUIRES EXPLICIT DECISION.**

Regardless of the outcome, the following are fixed and non-negotiable:
- original + successor/amendment provenance;
- reconstructable chain; no silent value change; reason required where the
  governing contract demands it; correction authorized under the Phase 8
  actor model (Decision 4).

## Decision 4 — Correction Actor / Scope

### RESOLVED — actor identity source

The correcting principal identity is taken **exclusively from the
authenticated context** (server-derived, via the existing authorization
infrastructure). It is **never** accepted from a client-supplied payload —
a forged actor identity is rejected; missing/invalid claims fail closed.

### UNRESOLVED — actor role / permission

Whether correction requires: a dedicated `results.correction` (or similarly
named) permission; a distinct reviewer role; and/or separation-of-duties so
the original verifier/finalizer cannot self-correct:
**REQUIRES EXPLICIT DECISION** — the permission name/code must follow the
established `laboratory.<resource>.<action>` convention (e.g.
`laboratory.results.correction`? — see below) and must only be added with
the minimum required Phase 8 scope. **No new permission is introduced until
this ADR's Decision 4 resolves the name/code and the authorization model.**

### RESOLVED — scope and isolation

- Every Phase 8 action is scoped to the acting principal's organization and
  facility, and enforced server-side.
- Cross-organization and cross-facility access is rejected.
- Forged organization/facility claims cannot expand scope (existing Phase
  4–7). Isolation remains.
- Correction cannot cross organization/facility boundaries.

### UNRESOLVED — permission naming

The exact permission code for correction (e.g.
`laboratory.results.correc` vs `laboratory.results.amend` ...) is not yet
decided. The convention `laboratory.<resource>.<action>` must be honored.
**REQUIRES EXPLICIT DECISION** — do not invent a code.

## Consequences

### Positive

- Explicit Phase 7 / Phase 8 boundary: Phase 7 result **entry** and
  observation completion remain untouched; Phase 8 adds validation /
  verification / finalization / controlled correction only.
- Concurrency, audit, authorization, provenance, and finalized-result
  immutability are preserved and no earlier migration/permission/API
  invariant changes.
- Structural validation is reused, not duplicated.
- No silent overwrite; no finalized-result mutation; history reconstructable.

### Negative

- The three UNRESOLVED decisions block Phase 8 implementation start until
  explicit clinical/clinical-governance decisions are made. This is
  intentional: Phase 8 must not proceed by guessing on clinical-safety
  semantics.

### Consequences not in Phase 8 scope

Reporting, diagnostic reporting, analyzer/device integration, HL7/FHIR/DICOM,
CDS, AI interpretation, and reference-range/rules authoring remain **outside**
Phase 8 (per authoritative ROADMAP + master-blueprint phase boundaries). No
invented clinical rules, reference ranges, critical-value flags, or CDS
behavior.

## Security implications

- Actor identity is server-derived; payload cannot forge the actor.
- Organization/facility isolation enforced; forged claims fail closed.
- Correction authorization is the minimum required and is not invented
  before Decision 4 resolves the permission code.
- No credentials, tokens, secrets, or PHI stored in audit metadata.

## Clinical-data-integrity implications

- Finalized results are immutable; only controlled correction (Decision 3)
  can alter the effective value, and only by creating a preserving
  successor/amendment record.
- Original provenance preserved; no silent overwrite; no deletion.
- History/provenance reconstructable independent of administrative audit.

## Persistence implications

- A Phase 8 migration may be required for the correction representation once
  Decision 3 resolves (successor identity vs. versioned amendment) and for
  any validation/verification/finalization state/timestamp fields once
  Decision 1 resolves. **No Phase 8 migration is created while the three
  UNRESOLVED decisions remain open.**
- Existing Phase 1–7 migrations, tables, and xmin concurrency config are
  preserved; no rewrite.

## API implications

- No Phase 8 API endpoints are added until Decisions 1–4 resolve.
- The `/v1/laboratory/results` Phase 7 route and DTOs are preserved;
  verification/finalization/correction operations are Phase 8 additions only,
  once authorized and decided.

## Testing implications

- Existing Phase 1–7 tests must continue to pass unchanged (no regression).
- Phase 8 test coverage (once decisions resolve): valid/invalid lifecycle
  transitions, editability, concurrency (simultaneous
  verify/finalize/correct), stale-version rejection, duplicate-transition
  rejection, authorization (forged claims, missing claims, cross-org,
  cross-facility), finalized-result immutability, correction history
  preservation, provenance, transaction atomicity — verified against
  disposable PostgreSQL.

## Explicit Phase 7 / Phase 8 boundary

- **Phase 7 (frozen, not modified):** result entry and observation
  completion — typed values, specimen/order-item/test-version association,
  `entered`-state editable update, structural validation, `results` table,
  migration `20260918035033_AddResultEntity`.
- **Phase 8 (authorized, not yet implemented):** result validation,
  verification, finalization, and controlled correction. Structural
  validation reused; clinical/process validation gate, verification,
  finalization, and correction semantics await Decisions 1, 3, 4.
